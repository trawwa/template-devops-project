# Постмортем: отладка multi-node деплоя и liveness-проб (MAIN-324)

**Дата:** 30 июля — 1 августа 2026
**Проект:** Local Cloud Platform (template-devops-project)
**Тикет:** MAIN-324 — Kubernetes: multi-node кластер, Service/Ingress, liveness/readiness

## Summary

При настройке multi-node кластера в minikube и тестировании liveness/readiness проб
столкнулся с четырьмя независимыми проблемами, каждая из которых маскировала
следующую. Итог — рабочий multi-node деплой с подтверждённым через Events
поведением liveness/readiness проб при искусственном сбое.

## Root cause (5 whys, по основному инциденту — недоступность второй ноды)

1. Почему вторая нода была NotReady? — CNI не проинициализировался на ней.
2. Почему CNI не проинициализировался? — кластер изначально поднимался как single-node 61 день назад, добавление ноды постфактум не гарантирует, что daemonset CNI корректно раскатится на неё в разумное время.
3. Почему не подождали дольше? — сравнение с состоянием control-plane (там CNI-под был) показало явную асимметрию, а не просто задержку.
4. Почему это стало проблемой, а не просто подождать? — время дебага реанимации старого кластера превысило бы время его пересоздания.
5. Первопричина: multi-node конфигурация была добавлена поверх кластера, изначально спроектированного и живущего как single-node, без переинициализации сетевого слоя.

| +ещё неделя | Внешний доступ через Ingress (`curl app.local/health`) — `Empty reply from server`, при этом `/etc/hosts` и конфиг Ingress валидны, `nginx-controller` подтверждает `Backend successfully reloaded` |
| — | Диагностика по цепочке: `port-forward` на Service — сработал (Service→Pod здоровы) → `minikube tunnel` — не помог (сервис `ingress-nginx-controller` типа `NodePort`, а не `LoadBalancer`, tunnel тут не при чём) → прямой `curl` на `NodePort` с хоста — тоже пусто → `kubectl exec` в app-под + `wget` на IP пода ingress-controller **изнутри кластера** — сработал, вернул `{"status":"ok"}` |
| — | Вывод: вся цепочка Ingress→Service→Pod исправна; проблема изолирована в последнем сегменте — Windows-хост → NodePort через `docker` driver |
| Финал 2 | Обходной путь: `minikube service ingress-nginx-controller -n ingress-nginx --url` — поднимает корректно проксируемый под Windows `localhost`-порт; `curl -H "Host: app.local" http://127.0.0.1:<PORT>/health` вернул `{"status":"ok"}` |
| — | Чистая версия теста без правки `hosts`-файла (который на Windows периодически откатывается антивирусом): `curl --resolve app.local:80:192.168.49.2 http://app.local/health` |

## Impact

- Потеряно ориентировочно 2-3 часа суммарно на диагностику четырёх независимых проблем
- Заблокирован прогресс по MAIN-324 на несколько дней (простой между сессиями усугубил ситуацию — состояние окружения "уехало" от последнего known-good)
- Положительный эффект: непреднамеренно получен более полный тест liveness-логики, чем планировался изначально (реальный "protracted incident" вместо однократной поломки)

## Что это дало (для портфолио / собеса)

Три технически конкретных, проверяемых на практике факта, которые не вычитать в
туториале:

1. **PID 1 и сигналы:** процесс без init-обвязки в контейнере может игнорировать
   даже SIGKILL, если сигнал приходит изнутри собственного PID-неймспейса
   (`kubectl exec` + `kill`). Снаружи (container runtime → SIGTERM/SIGKILL) сигнал
   сработает всегда. Практический вывод — использовать `tini`/`dumb-init` как
   entrypoint для процессов, которым важна предсказуемая обработка сигналов.

2. **`minikube docker-env` несовместим с multi-node кластерами** — официальное
   ограничение, не баг. Для сборки образов в multi-node нужно либо собирать на
   хосте и грузить через `image load`/`docker save` + tar, либо поднимать
   registry-addon.

3. **Docker layer cache завязан на хэш содержимого файла, а не на тег образа** —
   смена тега (`:latest` → `:v2`) сама по себе не инвалидирует кэш, если
   содержимое COPY-источника не изменилось. Источник путаницы, если полагаться
   на тег как индикатор "это новая версия".

4. **Windows + Docker Desktop + minikube `docker` driver не даёт прямого доступа
   с хоста к `NodePort` по IP ноды**, даже когда весь путь Ingress→Service→Pod
   технически исправен (что подтверждается тестом изнутри кластера). Это не баг
   конфигурации, а сетевая особенность связки — `minikube tunnel` тут не помогает,
   поскольку он рассчитан на `LoadBalancer`-сервисы, а `ingress-nginx-controller`
   по умолчанию — `NodePort`. Рабочий обход — `minikube service <name> -n <ns> --url`,
   который поднимает корректно проксируемый порт на `127.0.0.1`. Для повторяемого
   теста без правки системного `hosts`-файла (который на Windows периодически
   откатывается антивирусом) — `curl --resolve host:port:ip url`, подменяющий
   резолвинг DNS только для одного вызова curl.
